# ADR-004: Message Broker kiválasztása
- Státusz: Aktív

**In the context of**
- az aszinkron kommunikáció tervezésekor, ahol a Message Broker közös csatornát biztosít a médiafeldolgozáshoz (*Media Worker*), az auditnaplózáshoz (*Audit Service*) és az értesítésekhez (*Notification Service*), és ahol az Event Sourcing minta megköveteli, hogy az események tartósan megmaradjanak és visszajátszhatók legyenek

**Facing the need for**
- olyan üzenetközvetítő megoldásra, amely egyszerre kezeli a nagy áteresztőképességű eseményfolyamot, támogatja több független fogyasztó párhuzamos olvasását duplikáció nélkül, és az *Audit Service* számára kritikus visszajátszható eseménytörténetet biztosít — a Takarékosság ASR értelmében indokolatlan infrastrukturális többletköltség nélkül

**We decided for**
- Apache Kafka alkalmazása; a mérlegelés során három jelölt merült fel:
  - **RabbitMQ**: hagyományos, push-alapú ("okos bróker, buta fogyasztó") üzenetsor; a kézbesítés után törli az üzeneteket, így nem támogatja az Event Sourcing visszajátszási igényét, és fan-out esetén üzenetmásolatokat kell fenntartani
  - **Redis Streams**: könnyűsúlyú, log-alapú streaming; a Redis már jelen van a stackben (cache), de a két felhasználási mód keveri a felelősségeket, és tartós, nagy volumenű eseménytárolásra nem optimalizált
  - **Apache Kafka**: elosztott, append-only naplóra épülő platform ("buta bróker, okos fogyasztó"); az események tartósan megmaradnak lemezen, a fogyasztók pull-alapon, saját offsettel olvasnak, így több independent consumer group ugyanazt az eseménynaplót olvassa duplikáció nélkül

**Achieving**
- az *Audit Service* bármikor visszatekerheti az offsetjét és visszajátszhatja az eseménytörténetet, ha újraindul vagy egy új szolgáltatás kerül bevezetésre
- több független fogyasztó (*Notification Service*, *Audit Service*, *Media Worker*) párhuzamosan olvas ugyanabból az eseményfolyamból, duplikáció nélkül — az egyik elakadása nem befolyásolja a többit
- a szekvenciális lemez I/O és az üzenet-kötegelés (batching) másodpercenként millió nagyságrendű esemény feldolgozását teszi lehetővé; ez a terhelési szint RabbitMQ esetén memóriaproblémákhoz vezet
- a partíciók hozzáadásával az áteresztőképesség lineárisan skálázható, fogyasztói oldali változtatás nélkül

**Accepting that**
- a Kafka klaszter üzemeltetése (partíciók, replikációs faktor, KRaft konszenzus mechanizmus) összetettebb, mint egy hagyományos RabbitMQ szervere
- a fejlesztőknek ismerniük kell a partíció-, consumer group- és offset-kezelés működését — ez magasabb belépési küszöböt jelent
- a Kafka nem rendelkezik beépített komplex üzenet-útválasztással (pl. fejléc vagy regex alapú routing); ezt alkalmazásszinten vagy a Kafka Streams API-val kell megoldani
